# AGENTS.md — ExecutionDM

Guidelines for AI coding agents (GitHub Copilot, Codex, Claude, etc.) working in this repository.
Read this file before making any changes.

---

## 1. Project Overview

**ExecutionDM** is an [IVOA](https://www.ivoa.net/) standards project that defines a **data-model-first** representation of computational task execution for the Virtual Observatory.

- The primary artefact is a [VO-DML](https://ivoa.github.io/vo-dml/) model described in VODSL source files.
- Generated artefacts (Java classes, XSD, JSON Schema, OpenAPI YAML, TAP schema) are produced by the Gradle build; they **must never be edited by hand**.
- Accompanying documentation lives under `doc/site/` and is published with MkDocs.
- The product requirements are tracked in `doc/site/requirements.md`.

## 4. Build and Test Commands

```bash
# Compile model, generate Java, run XML/JSON round-trip tests
./gradlew test

# Build all schema artefacts (XSD, JSON Schema, OpenAPI YAML, TAP schema)
./gradlew vodmlSchema

# Generate VO-DML XML from VODSL sources
./gradlew vodslToVodml

# Generate the full documentation site and serve locally at http://localhost:8000
./gradlew testSite

# Deploy the site to GitHub Pages
./gradlew doSite
```

> **Always run `./gradlew test` after any model change** to verify round-trip serialisation.

## 5. Model Authoring Rules (VODSL)

The three VODSL source files and their responsibilities are:

| File | Model prefix | Purpose |
|------|-------------|---------|
| `ExecutionDM-v1.vodsl` | `execution` | Core job lifecycle, resources, I/O |
| `ParameterDM-v1.vodsl` | `pdl` | Parameter / PDL type system (inputs and outputs) |
| `ToolDM-v1.vodsl` | `tool` | Tool image model (OCI registry, build, discovery, interface) |

`ExecutionDM-v1.vodsl` includes both `ToolDM-v1.vodsl` and `ParameterDM-v1.vodsl`; `ToolDM-v1.vodsl` includes `ParameterDM-v1.vodsl`.  Dependency direction is: `execution → tool → pdl`.

1. **Edit only the VODSL sources** in `model/`. The VO-DML XML in `vo-dml/` is either committed after generation or generated during the build — never edit it directly.
2. **Generated files in `build/` are never committed.** The `.gitignore` should (and does) exclude the `build/` directory.
3. **VODSL syntax quick reference:**
   - `otype` = object type (identity semantics)
   - `dtype` = data type (value semantics, no identity)
   - `abstract otype` = abstract base type
   - `primitive` = scalar leaf type
   - `enum` = enumerated type
   - Multiplicity suffixes: none = `[1,1]`, `@?` = `[0,1]`, `@*` = `[0,*]`, `@+` = `[1,*]`
   - `as composition` = strong ownership (child cannot exist without parent)
   - `references` = weak reference (child can exist independently)
4. All new types **must have a non-empty description string**.
5. New types that represent exchangeable resources should extend from appropriate IVOA base types where applicable.
6. Follow the **black-box principle**: the model describes inputs, outputs, and execution context — never internal algorithmic behaviour inside a container.
7. Do not add `resource booking`, `reservation`, or `interactive session` concepts without explicit approval — these are in-scope non-goals per the PRD (see `doc/site/requirements.md`).

## 6. Binding and Code Generation

The Java binding is configured in `vo-dml/ExecutionDM-v1.vodml-binding.xml`:

- Java package root: `org.ivoa.dm.execution`
- XML namespace: `http://ivoa.net/dm/execution/v0.1`

When adding a **new model file** to the build:

1. Add the `.vodsl` file to `model/`.
2. If a separate VO-DML XML file is needed, add it to `vo-dml/`.
3. Add a corresponding `<model>` block to `vo-dml/ExecutionDM-v1.vodml-binding.xml`.
4. Update the `vodml { bindingFiles.setFrom(...) }` block in `build.gradle.kts` if the binding file changes.

## 7. Test Conventions

- Tests live in `src/test/java/org/ivoa/dm/execution/`.
- Use `AutoRoundTripWithValidationTest<M>` as the base class for model round-trip tests; it validates XML and JSON serialisation automatically.
- Override `createModel()` to instantiate a representative model instance with realistic data.
- Override `testModel(M model)` to add domain-specific post-round-trip assertions.
- Use JUnit 5 (`@Test`, `@BeforeEach`, etc.).
- Do **not** add test data files to `build/`; use `src/test/resources/` instead.

## 8. Documentation Conventions

- All documentation source pages live under `doc/site/` in Markdown.
- `mkdocs.yml` is **generated** by the `makeSiteNav` Gradle task from `mkdocs_template.yml` — do not edit `mkdocs.yml` directly.
- When adding a new documentation page:
  1. Add the `.md` file to `doc/site/`.
  2. Add its entry to the `nav:` section of `mkdocs_template.yml`.
- Write in British English spelling (prioritise, artefact, behaviour, modelling) to match the existing PRD tone.
- Link to the requirements document (`requirements.md`) when a design decision traces to a `REQ-*` item.
- Use `doc/site/design-log/requirements-detail.md` for requirement-level detail and acceptance criteria that back the PRD narrative.
- Use `doc/site/design-log/decisions.md` for architectural decisions (ADR-style records).
- Use `doc/site/design-log/rfc.md` for **proposed** changes only; after implementation, remove/close the RFC entry and transfer the outcome to `CHANGELOG.md` and (if needed) `decisions.md`.
- Do not add auto-generated content (PlantUML diagrams, schema excerpts) manually — these are produced by the build.

## 9. Change Management Conventions

- `TODO.md` tracks short-term actionable tasks; keep entries concise and checkbox-based (`- [ ]`).
- `CHANGELOG.md` follows **Keep a Changelog** and **Semantic Versioning**:
  - Add entries under `## [Unreleased]` for notable user-visible changes.
  - Keep phrasing clear and implementation-focused (what changed and why it matters).
- For substantial model or API behaviour changes, follow this sequence:
  1. Capture proposal in `doc/site/design-log/rfc.md`.
  2. If accepted, record durable decision in `doc/site/design-log/decisions.md`.
  3. Implement code/model/docs changes.
  4. Update `CHANGELOG.md` in `Unreleased`.
- Keep `doc/site/design-log/requirements-detail.md` aligned with `REQ-*` identifiers in the PRD.

## 10. Scope and Design Constraints

Agents must respect the product boundaries defined in `doc/site/requirements.md`:

| Constraint | Status |
|-----------|--------|
| Batch job execution | **In scope** |
| Model-first / API-derived-second | **In scope** |
| Containerised black-box execution | **In scope** |
| Input/output / data-locator concepts | **In scope** |
| Resource matching (CPU/RAM/GPU/storage) | **In scope** |
| Interactive session lifecycle | **Out of scope (initial)** |
| Resource booking / reservation | **Out of scope (initial)** |
| Deep ExecutionBroker interop mapping | **Deferred** |
| Internal container behaviour | **Out of scope (by design)** |

Any model change that touches an out-of-scope area must include a comment linking to the open decision (`DEC-*`) in `requirements.md` that governs it.

## 12. What Agents Should NOT Do

- **Do not edit files under `build/`** — they are generated artefacts.
- **Do not edit `mkdocs.yml`** directly — edit `mkdocs_template.yml` instead.
- **Do not edit `vo-dml/*.vo-dml.xml`** directly — edit the corresponding `.vodsl` source.
- **Do not commit credentials** — `UKSRC_REPO_USERNAME` / `UKSRC_REPO_PASSWORD` are environment variables; never hardcode them.
- **Do not introduce interactive-session or reservation model elements** without an explicit `REQ-*` or `DEC-*` entry approving it.
- **Do not break the round-trip test** — always run `./gradlew test` before declaring a model change complete.
- **Do not leave implemented items in `doc/site/design-log/rfc.md` as open proposals** — migrate outcomes to `CHANGELOG.md` and decision records as appropriate.
- **Do not bypass `CHANGELOG.md` for notable changes** — keep `Unreleased` current.
- **Do not treat `TODO.md` as a design record** — place durable rationale in design-log documents.
